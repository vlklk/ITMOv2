# GitHub Spec Kit и OpenSpec: сравнение на одной фиче

Фреймворк для ДЗ — **GitHub Spec Kit v1.2.3**: официальные шаблоны и промпты команд из тега `v1.2.3` (MIT) в `practices/practice_04/tetris/.specify/`. OpenSpec разбирали на практике 5 (презентация `prenetation.pdf`). Фича одна — «Режимы игры и всплывающие подписи» в Тетрисе из ДЗ 4.

> **Ограничение.** CLI `specify` и bash-скрипты Spec Kit в этой среде не запускались: политика безопасности агента запрещает исполнять скачанный внешний код. Агенты выполняли промпты команд вручную — создавали `specs/NNN-…/` и `.specify/feature.json` сами (`.specify/README.md`). CLI `openspec` тоже не запускался: сведения о нём — из материалов практики.

## Модель работы

| | Spec Kit | OpenSpec |
|---|---|---|
| Единица работы | Фича: каталог `specs/NNN-short-name/` с полным набором документов | Изменение (change): папка с proposal и дельтой к текущим specs |
| Цикл | `constitution` → `specify` → `clarify` → `plan` → `tasks` → `analyze` → `implement` | `explore` → `propose` → review человеком → `apply` → проверки → `sync` / `archive` |
| Постоянные правила проекта | `.specify/memory/constitution.md` — принципы с уровнями MUST и версией; Constitution Check в `plan` и `analyze` | `openspec/config.yaml` → `rules` (например, `rules.design: Mermaid`) — подмешиваются в инструкции |
| Что после реализации | Спека остаётся в каталоге фичи; отдельного слияния в «главную» спеку нет | `sync` переносит дельту в main specs, `archive` сохраняет изменение в истории |
| Проверка документов | `/speckit.analyze`: только чтение, ID находок, severity, покрытие требований задачами | `openspec validate` и `status` проверяют структуру (CLI без LLM) |
| Где сильнее | Зелёное поле и крупная фича: план с `research`, `data-model`, `contracts`, `quickstart` | Существующий проект (brownfield): маленькие изменения поверх живых specs |

## Что показала практика на этой фиче

**Сильные стороны Spec Kit, которые реально пригодились:**

1. **Конституция с Constitution Check.** Пять принципов записаны один раз (чистая логика, TDD, литералы в тестах, без зависимостей, дизайн-токены). Каждый `plan` проверял себя по ним. Именно по принципу II `/speckit.analyze` нашёл CRITICAL: в сценарии E10 ожидаемые очки считал тот же код, что их выдаёт.
2. **Маркеры `[NEEDS CLARIFICATION]` с лимитом в 3.** Обе команды вынесли спорные места в явные вопросы: 2 у UI, 3 у логики. Все пять стали строками согласования в контракте, а не тихими допущениями.
3. **`/speckit.analyze` как независимый ревьюер артефактов.** 19 находок по 81 требованию и 83 задачам, покрытие 100%. Три HIGH ловили бы баги в коде: `NaN` в колонке спринта при `topOut`, неверное ожидание «0:01» вместо «0:01,0», сценарий E8, который не дошёл бы до `timeUp`.
4. **Артефакты плана.** `data-model.md` и `research.md` (R1–R16 в формате Decision / Rationale / Alternatives) объясняют решения сверх спецификации — их потом подхватил HANDOFF.

**Чего не хватило и где OpenSpec удобнее:**

1. **Две команды — одна фича.** В Spec Kit «фича = каталог», общего места для контракта между двумя фичами нет. Контракт пришлось вынести в `specs/shared/game-modes-contract.md` вне шаблонов. В OpenSpec две спеки одной capability естественнее легли бы в одно изменение с дельтами к двум specs.
2. **Brownfield.** Спеки Spec Kit пишутся «с нуля» для фичи; старые требования A и B живут в `docs/requirements.md` и не обновляются автоматически. Пришлось вручную дописать раздел «Фича C» по находке M7. В OpenSpec `sync` обновил бы основную спецификацию сам.
3. **Нет архива.** После `implement` в Spec Kit нет шага, который фиксирует «теперь это текущее поведение системы». У OpenSpec это `archive`.
4. **Тяжесть.** 7 команд и 6 документов на фичу — много для маленького изменения. Для правки в одну строку OpenSpec с `propose` → `apply` легче.

## Вывод

Для фичи, которую делали две команды с общим контрактом и сложными граничными случаями (время, переполнение, рекорды), Spec Kit дал больше: конституция и `analyze` нашли ошибки до кода. Для дальнейшего сопровождения того же Тетриса — маленьких правок поверх уже работающих режимов — я бы выбрал OpenSpec: дельты и `archive` держат одну актуальную спецификацию, а не набор каталогов фич.
