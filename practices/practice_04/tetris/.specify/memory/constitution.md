# Тетрис Constitution

## Core Principles

### I. Чистая детерминированная логика и разделение слоёв

- Вся игровая логика MUST находиться в `src/game.js` и состоять из чистых функций над обычным
  объектом состояния: функция получает состояние и возвращает новое, не изменяя переданное.
- В `src/game.js` MUST NOT быть DOM, таймеров и `Math.random`. Случайность — только из
  переданного seed (генератор «мешок из 7» на mulberry32); при одинаковом seed
  последовательность фигур одинакова.
- Побочные эффекты хранилища (рекорд в `localStorage`) MUST находиться только в `src/record.js`.
  Хранилище передаётся параметром; сбои хранилища MUST NOT выбрасываться наружу — модуль
  возвращает `null` («играем без рекорда») или последнее прочитанное значение.
- DOM, клавиатура, касания, таймеры (`requestAnimationFrame`, `setTimeout`) и получение
  `window.localStorage` MUST находиться только в `src/ui.js`; игровых правил в нём нет.

Обоснование: чистая логика проверяется в `node` без браузера, а воспроизводимость по seed
делает тесты и отладку детерминированными.

### II. Тесты публичных функций, сначала тест (NON-NEGOTIABLE)

- Новая или изменённая логика в `src/game.js` MUST разрабатываться по TDD: сначала падающий
  тест, затем код (skill `.claude/skills/test-driven-development/`, `SKILL.md` и
  `writing-good-tests.md`).
- Тесты MUST проверять публичные (экспортируемые) функции `src/game.js` и `src/record.js`.
- Функции `src/record.js` MUST тестироваться с подменой хранилища — объектом с интерфейсом
  Web Storage (`getItem`/`setItem`), включая вариант, бросающий ошибки.
- Ожидаемые значения MUST быть литералами, посчитанными вручную, а не вычисленными тем же кодом.
- Форма теста: `node:test` + `node:assert/strict`, одно поведение на тест; имя теста по
  требованию MUST начинаться с ID требования (например, `A4: две строки за раз дают 300 ×
  уровень`).
- Тесты MUST NOT удаляться или ослабляться ради зелёного результата; при падении исправляется
  код, а не тест.

Обоснование: тесты — единственный автоматический способ доказать соответствие контракту A/B;
ручные литералы исключают «тест, повторяющий реализацию».

### III. Контракт требований с ID

- `docs/requirements.md` — источник истины о поведении игры. Каждое требование имеет ID
  (`A1`…`A9`, `B1`…`B4`) и способ проверки: unit-тест, проверка в браузере или скриншот.
- Требования с проверкой «unit-тест» MUST быть покрыты тестами, имена которых содержат их ID.
- Изменения MUST NOT ломать уже реализованные сценарии: все сценарии фичи A продолжают
  работать при любой новой фиче (B4 — `sh scripts/check.sh`).
- `docs/requirements.md` MUST NOT меняться без явного поручения пользователя.
- Решения сверх спецификации фиксируются в `docs/HANDOFF.md` как открытые вопросы для
  подтверждения, а не молча.

Обоснование: трассировка «ID требования → тест» делает проверку контракта механической.

### IV. Без зависимостей и сборки

- Проект MUST оставаться на чистом JavaScript (ES-модули), статическом HTML/CSS и
  `node --test`; `package.json` не содержит зависимостей.
- MUST NOT подключаться npm-зависимости, сборщики, фреймворки и CDN-скрипты без явного
  поручения. Исключение: веб-шрифты Google Fonts; при их недоступности работают системные
  запасные шрифты, указанные в CSS-переменных.
- Игра открывается статическим сервером: `python3 -m http.server 5173` в корне проекта.

Обоснование: нулевые зависимости — нулевая поверхность поставки и мгновенный запуск без
установки.

### V. Дизайн-токены и доступный интерфейс

- Цвета, размеры клетки и шрифты MUST быть CSS-переменными в `:root` файла `src/styles.css`;
  в остальном CSS — только ссылки на них (`var(--…)`), включая адаптивные переопределения
  переменных в `@media`.
- Интерфейс MUST следовать skill `frontend-design`: собственная визуальная идея (сейчас —
  «тетрадь в клетку», план в `docs/design-plan.md`), а не шаблон; сначала план, затем код,
  затем самокритика по скриншоту.
- Интерфейс MUST работать от ширины 360 px, иметь видимый фокус клавиатуры (`:focus-visible`)
  и отключать декоративную анимацию при `prefers-reduced-motion: reduce` (A9).

Обоснование: токены дают единый источник визуальных решений, а A9 закрепляет доступность как
требование контракта.

## Стек и среда

- Язык и модули: JavaScript ES-модули в браузере (`<script type="module">`) и в Node.js
  (`"type": "module"` в `package.json`).
- Структура: логика `src/game.js`, рекорд `src/record.js`, интерфейс `index.html`, `src/ui.js`,
  `src/styles.css`; тесты `tests/*.test.js`; правила `AGENTS.md`, `docs/style-guide.md`;
  контракт `docs/requirements.md`.
- Тестирование: встроенный `node:test` и `node:assert/strict`, без тестовых библиотек.
- Запуск: `python3 -m http.server 5173` → `http://localhost:5173/`; для агента — MCP
  встроенного браузера (`preview_start` с `name: "tetris"`).

## Процесс разработки и ворота качества

- Единственная команда проверки — `sh scripts/check.sh` (`node --test` по `tests/*.test.js`);
  результат MUST быть exit 0 перед сдачей работы. `scripts/check.sh` MUST NOT ослабляться.
- После каждой правки файла хук `.claude/hooks/check-after-edit.sh` запускает проверку сам;
  при `FAIL` исправляется причина в коде, а не тест.
- Изменения интерфейса MUST проверяться в браузере: скриншот через MCP встроенного браузера и
  `read_console_messages` — в консоли нет ошибок.
- Перед любым изменением кода читается `docs/style-guide.md`.
- Без явного поручения MUST NOT: менять `docs/requirements.md`, `scripts/check.sh`, `.claude/`
  и `AGENTS.md`; удалять или ослаблять тесты; подключать зависимости; делать `git commit`,
  `git push`, `git merge`.

## Governance

- Конституция закрепляет правила, уже действующие в `AGENTS.md`, `docs/style-guide.md` и
  `docs/requirements.md`, и не заменяет их: эти файлы остаются рабочими инструкциями. При
  расхождении действует более строгое правило, а расхождение устраняется поправкой.
- Поправки вносятся только по явному поручению пользователя через `/speckit.constitution`;
  исходные файлы правил при этом меняются тоже только по явному поручению.
- Версионирование — семантическое: MAJOR — удаление или переопределение принципа; MINOR —
  новый принцип или раздел либо существенное расширение; PATCH — уточнения формулировок.
- Соответствие проверяется в разделе «Constitution Check» плана (`/speckit.plan`) и командой
  `/speckit.analyze`; нарушение принципа в плане MUST быть обосновано в разделе сложности
  плана или устранено.
