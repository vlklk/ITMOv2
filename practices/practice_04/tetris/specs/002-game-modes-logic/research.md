# Research: Режимы игры и события для подписей — логика

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Контракт**: [`specs/shared/game-modes-contract.md`](../shared/game-modes-contract.md) v1.0

Открытых вопросов (NEEDS CLARIFICATION) в Technical Context нет: правила наружу закреплены контрактом §2 (строки Р-1…Р-26). Ниже — решения о том, как выполнить контракт внутри существующих модулей, с учётом текущего кода `src/game.js`, `src/record.js` и тестов `tests/*.test.js`. Внешних технологий и зависимостей фича не добавляет, поэтому задач «best practices» по ним нет.

## R1. Источник игрового времени

- **Decision**: логика получает время только приращением `advanceTime(state, deltaMs)`; `elapsedMs` — сумма приращений.
- **Rationale**: принцип I (в `src/game.js` нет часов); совпадает с циклом `frame()` в `src/ui.js`, который уже меряет дельту кадра и ограничивает её 1000 мс; контракт Р-7.
- **Alternatives considered**: абсолютное время от UI (`now − start`) — UI пришлось бы помнить начало и вычитать паузы, два источника истины; таймер внутри логики — нарушает принцип I.

## R2. Как гарантировать «в новом объекте только события этого вызова»

- **Decision**: внутренняя функция сборки нового состояния всегда задаёт `events` (переданный список или `[]`); все публичные функции, которые возвращают изменённое состояние (`moveLeft`, `moveRight`, `rotate`, `hold`, `tick`, `softDrop`, `hardDrop`, `advanceTime`), строят его через неё. Ветки «ничего не изменилось» возвращают вход как есть (`===`).
- **Rationale**: сейчас `tryPlace` и `rotate` делают `{ ...state, active }` — без явного сброса прежние `events` перетекли бы в следующий объект и UI показал бы подпись дважды (контракт §2.2, правило объекта, Р-5). Одна точка сброса проще проверить тестом на каждую функцию.
- **Alternatives considered**: сбрасывать `events` в UI — нарушает Р-5 (UI только читает); хранить счётчик вызовов — лишнее поле.

## R3. Проверка «партия окончена»

- **Decision**: все функции по-прежнему проверяют `state.over`; новые исходы выставляют и `outcome`, и `over: true` одновременно, инвариант `over === (outcome !== "playing")` поддерживается только в логике.
- **Rationale**: тесты A6 и B2 (`tests/game.test.js`, `tests/assist.test.js`) создают окончённую партию как `{ ...state, over: true }` без `outcome` и ждут, что ходы ничего не меняют; проверка по `outcome` сломала бы их (B4, принцип II — тесты не меняются).
- **Alternatives considered**: проверять `outcome !== "playing"` — ломает 2 существующих теста.

## R4. Порядок шагов фиксации (`lockPiece`)

- **Decision**: 1) записать фигуру в поле; 2) убрать строки (`cleared`); 3) очки за строки по уровню **до** фиксации (как сейчас); 4) `combo` = `cleared > 0 ? combo + 1 : 0`; 5) «Подряд» = `cleared === 4 && backToBack` (до фиксации); новое `backToBack` = `cleared === 4 ? true : cleared > 0 ? false : backToBack`; 6) бонусы: комбо 50 × (combo − 1) × уровень при combo ≥ 2, «Подряд» 400 × уровень; 7) `lines`, `level` по A5, `linesToGoal`; 8) события в порядке `tetris`, `backToBack`, `combo`, `levelUp`; 9) в `sprint` при `lines ≥ 40` — исход `sprintFinish`, `result = Math.round(elapsedMs)`, событие `sprintFinish` последним; 10) иначе появление следующей фигуры и проверка `topOut` (A6); 11) `result` для `topOut`: `score` в `marathon`/`ultra`, `null` в `sprint`.
- **Rationale**: прямо отражает FR-011…016, FR-020…024, FR-041 и контракт §2.4–2.5; финиш проверяется до переполнения (Р-22). Очки по уровню до фиксации — уже принятое решение (`docs/HANDOFF.md`).
- **Alternatives considered**: проверять переполнение раньше финиша — противоречит Р-22.

## R5. Окончание ультры по времени

- **Decision**: `advanceTime` в `ultra` считает `elapsedMs = min(120000, elapsedMs + deltaMs)`; при достижении 120 000 — `outcome: "timeUp"`, `over: true`, `result: score`, `remainingMs: 0`, `events: [{ type: "timeUp", bonus: 0, score }]`; активная фигура остаётся как есть и не фиксируется.
- **Rationale**: FR-014, контракт §2.3; UI вызывает `advanceTime` до гравитации (Р-9), поэтому лишней фиксации в последнем кадре нет.
- **Alternatives considered**: проверять время в `tick` — время пришлось бы передавать в каждую функцию.

## R6. Точность времени

- **Decision**: `elapsedMs` хранится без округления; `result` спринта и `timeMs` события — `Math.round(elapsedMs)` один раз на финише; рекорды сравниваются в целых мс.
- **Rationale**: покадровое округление копит ошибку (Р-8); SC-003 — точность 1 мс.
- **Alternatives considered**: округлять каждое приращение — до ~30 мс ошибки за секунду при 60 кадрах.

## R7. Где хранится направление сравнения рекорда

- **Decision**: `src/record.js` импортирует `MODES` из `src/game.js` и берёт `better` и проверку id оттуда; ключи — таблица в `src/record.js` (`marathon` → `tetris.record`, `sprint` → `tetris.record.sprint`, `ultra` → `tetris.record.ultra`).
- **Rationale**: один источник параметров режимов; импорт неизменяемой константы не добавляет побочных эффектов (принцип I); ключи хранения — забота модуля хранилища.
- **Alternatives considered**: дублировать `better` в `src/record.js` — два места для одного правила.

## R8. Тестирование бонусов без новых экспортов

- **Decision**: функции расчёта бонусов не экспортируются; бонусы проверяются через `hardDrop`/`tick` на подготовленных полях (`combo`, `backToBack`, `level` задаются в состоянии, как это уже делает `stateWith` в тестах), с ручными литералами очков.
- **Rationale**: контракт §2.3 перечисляет публичные функции; тест поведения через фиксацию проверяет и порядок событий, и прибавку `score`.
- **Alternatives considered**: экспортировать `comboBonus`/`backToBackBonus` как `lineClearPoints` — расширяет публичный API сверх контракта.

## R9. Раскладка и имена тестов

- **Decision**: новые файлы `tests/contract.test.js`, `tests/modes.test.js`, `tests/scoring.test.js`, `tests/events.test.js`, `tests/mode-record.test.js`; имена начинаются с ID: `LG FR-011: …`; контрактные — `LG FR-044 (§2.1): …` и т. п. Существующие файлы тестов не трогаются.
- **Rationale**: принцип II (ID в имени); `scripts/check.sh` уже подхватывает `tests/*.test.js`; `LG` различает требования логики и UI, как в контракте.
- **Alternatives considered**: дописывать в `tests/game.test.js` — смешивает A и новую фичу и рискует случайно изменить тесты B4.

## R10. Неизменяемость `MODES`

- **Decision**: `MODES` — `Object.freeze` массива и каждого элемента.
- **Rationale**: контракт §2.1 — «неизменяемый массив»; UI строит из него экран и не должен случайно его испортить.
- **Alternatives considered**: функция `getModes()` — лишний вызов, контракт называет константу.

## R11. Определение `levelUp`

- **Decision**: событие `levelUp` с `level = levelForLines(lines после)`, если оно больше `level` до фиксации; одна фиксация (≤ 4 строки) не может поднять уровень больше чем на 1.
- **Rationale**: A5 и FR-006; во всех режимах (Р-3).

## R12. Проверка `deltaMs`

- **Decision**: принимается только `typeof deltaMs === "number" && Number.isFinite(deltaMs) && deltaMs > 0`; иначе — тот же объект. Верхняя граница 1000 мс логикой не проверяется — это гарантия UI (контракт §2.3).
- **Rationale**: FR-008, Р-24; ограничение 1000 мс в логике изменило бы смысл переданного времени молча.
- **Alternatives considered**: бросать исключение — противоречит Р-24.

## R13. Состояние после финиша спринта

- **Decision**: при `sprintFinish` следующая фигура всё равно выставляется в точку появления (как при обычной фиксации), даже если пересекает занятые клетки; `over: true` блокирует дальнейшие вызовы.
- **Rationale**: контракт §2.5 описывает, как UI рисует такую фигуру; не нужно отдельной ветки «без активной фигуры».

## R14. Производные поля

- **Decision**: `linesToGoal` пересчитывается при каждой фиксации (`sprint`: max(0, 40 − lines), иначе `null`); `remainingMs` — при каждом `advanceTime` (`ultra`: max(0, 120000 − elapsedMs), иначе `null`); оба задаются в `createGame`.
- **Rationale**: UI читает готовые поля (FR-043), не повторяя правил.

## R15. Неподходящий `result` в `saveModeRecord`

- **Decision**: неизвестный `modeId` → `RangeError` до обращения к хранилищу; если хранилище недоступно для чтения → `null`; `result`, не являющийся целым > 0 (включая 0 и `null`), рекордом не становится и не записывается: `{record: current, previous: current, isNew: false}`.
- **Rationale**: FR-032, FR-033, Р-19; UI не вызывает сохранение при `result === null`, но функция не должна падать или писать мусор.
- **Alternatives considered**: `RangeError` на `null` — исключение для штатной ситуации «проигранный спринт».

## R16. Совместимость `readRecord`/`saveRecord`

- **Decision**: существующие функции остаются без изменений; `readModeRecord(storage, "marathon")` читает тот же ключ `tetris.record` и даёт то же значение, что `readRecord(storage)`.
- **Rationale**: Р-25, тесты B3 не меняются (принцип II); миграция не нужна (Р-18).
