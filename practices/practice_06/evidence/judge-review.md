# Вердикт судьи по практике 6 (Mini Shop)

Оценка выполнена по системному промпту судьи (`judge-system-prompt.md`). Проверены
`THREAT_MODEL.md`, `REPORT_01.md`, `REPORT_02.md`, сверено с `lab/service.py`,
`lab/sandbox.py`, доказательствами в `evidence/before/` и `evidence/after/` и
прогоном тестов. Документы оценивались строго по доказательности, пересказ не
засчитывался.

## Вердикт

**Принято с замечаниями.** Покрытие близко к полному, исправления устраняют
первопричины, доказательная база воспроизводима (прогон `make step6` → 39 тестов
OK подтверждён независимо). Снижение — за один незакрытый доказательством пункт
контрольного списка: SQL-инъекция через `order_id` в `GET /assistant/context` не
продемонстрирована отдельной атакой ни в REPORT_01, ни в REPORT_02 (есть только в
модели угроз).

## Подтверждённые пробелы

1. **SQLi через `order_id` в `GET /assistant/context` не доказана.** В контрольном
   списке это отдельный пункт. В модели угроз он есть (TM #11, параметр в f-строке
   `WHERE id = {order_id}` в исходной версии), но ни REPORT_01, ни REPORT_02 не
   показывают запрос вида `order_id=0 OR 1=1` (или UNION) с фактическим ответом,
   где в prompt попадает чужой/произвольный заказ. Это единственная заявленная
   инъекция без воспроизведения. В REPORT_02 эта точка тоже не переатакована,
   хотя в коде она уже исправлена (`WHERE id = ? AND owner = ?`,
   `service.py:153-154`).

2. **Подчинение LLM инъекции не воспроизведено** (частичный, но честно
   задокументированный пробел). Факт (а) «модель подчинилась отзыву» не показан:
   `opencode/big-pickle` недоступна (нет учётных данных, `pi_answer_clean.err`).
   Это не вина автора и по рубрике допустимо, т.к. вывод «сервер уязвим» опирается
   на факт (б) — серверный контроль доступа. Но строго формально сама цепочка
   «отзыв → решение модели» остаётся гипотезой.

## Ложные или слабые утверждения

Грубых ложных утверждений не обнаружено; проверенные заявления воспроизводимы.
Слабые места:

- **REPORT_02, п.6 / `after/06_files_traversal.txt`:** для `user=../private&path=operator-note.txt`
  ответ `internal server error` объясняется тем, что `user` игнорируется и сервер
  пытается прочитать несуществующий `files/alice/operator-note.txt`, а не тем, что
  сработала проверка traversal. Это корректно (служебная заметка не утекла, текст
  ошибки обобщён), но собственно блокировка traversal доказывается не этой строкой,
  а соседними (`path=../private/...` → `403 forbidden path`). Формулировка слегка
  смешивает два механизма; на вывод не влияет.
- **Ссылки на строки `service.py` в TM и REPORT_01** (например `service.py:57`,
  `99-109`) относятся к версии ДО исправлений и не сверяемы с текущим (уже
  исправленным) файлом — рабочая копия содержит только пофикшенную версию.
  Это свойство задачи (до/после), а не ошибка, но проверяется лишь косвенно (по
  согласованности с `evidence/before/`).

Разбор prompt injection выполнен корректно по сути: автор явно разделяет (а)
послушание модели и (б) исполнение опасного решения сервером и строит вывод
«сервер уязвим» именно на (б) — изготовленный вручную JSON с токеном alice
исполняет `delete_tree`/`export_profiles`/`read_file` без проверки (подтверждено
`before/10c_execute_delete.txt`, `pi_manual_execute.txt`). Это валидная находка
по критерию 3 промпта судьи.

## Качество мер и проверки исправлений (критерий 4)

Проверено по коду и `evidence/after/` — меры устраняют причину, а не симптом:

- владелец и роль берутся только из серверной сессии (`service.py:96-98,124,132`),
  `id`/`user`/`X-Role` из запроса игнорируются;
- SQL параметризован везде (`WHERE id = ?`, `LIKE ?`, `order_id` как параметр);
- вывод отзывов экранируется `html.escape` (`service.py:147`);
- инструменты помощника авторизуются по сессии владельца: `read_file` — только
  свои файлы, `export_profiles` — только staff, `delete_tree` удалён как инструмент
  (`service.py:171-184`);
- опасное решение отклоняется независимо от послушания модели (`403` на forced-JSON,
  подтверждено `after/10c`, `after/pi_after.txt`);
- стенд не ослаблен: `sandbox.py` не менялся (физическая граница путей цела),
  сервер слушает только `127.0.0.1` (`service.py:229`);
- `/debug/logs` обезличен — в журнал пишутся только `method/path/status`
  (`service.py:76-77`), доступ только staff; тела/пароли/токены не сохраняются.

REPORT_02 повторяет те же 10 атак тем же вводом с парами before/after и отдельно
показывает принудительную передачу опасного решения в обход модели. Прогон тестов
подтверждён независимо: `make step6` → **Ran 39 tests — OK** (16 поставляемых + 23
регрессии безопасности в `test_security.py`).

## Модель угроз по существу (критерий 5)

Сильная: есть описание системы и акторов, таблица эндпоинтов, хранилища и поток
данных, DFD (mermaid) с явными доверенными границами TB1–TB5, список активов,
систематизация по STRIDE и привязка каждой угрозы к активу и мере, отдельный
раздел «как проверять меры». Соответствует ориентиру Microsoft Threat Modeling.

## Рекомендации (по приоритету)

1. **Добавить в REPORT_01 (и повтор в REPORT_02) отдельную атаку на `order_id`
   SQLi** в `GET /assistant/context`: запрос `order_id=0 OR 1=1` / UNION с
   фактическим ответом до фикса и `[]`/только-свой-заказ после фикса. Это
   закрывает единственный незадоказанный пункт контрольного списка.
2. В REPORT_02 §6 переформулировать строку `user=../private`: пояснить, что
   `internal server error` — следствие игнорирования `user`, а блокировка traversal
   доказывается строками с `path=../...` → `403`.
3. (Опционально) явно пометить в TM/REPORT_01, что номера строк относятся к версии
   до исправлений, со ссылкой на git-коммит исходного `service.py`, чтобы ссылки
   были сверяемы.
4. (Опционально, не вина автора) при появлении доступа к модели — приложить прогон,
   показывающий факт (а) подчинения LLM, чтобы цепандроить цепочку prompt injection
   целиком.
