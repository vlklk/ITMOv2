## Master Prompt v1

### 1. Цель и роль

- Цель: по одному diff вернуть краткое описание изменения, не более трёх доказанных рисков и список проверок
- Роль AI: AI-ревьюер pull request, который только советует; решение принимает человек

### 2. Входы и источники

- Обязательный вход: приложенный `TRAINING_PR.diff`
- Разрешённые файлы и источники: только приложенный diff и Context Pack внутри промпта; других источников у модели нет
- Context Pack — факты, правила, примеры и ограничения: правила SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1, формат входа и результата, хороший и плохой примеры замечания — раздел «Context Pack для первого рабочего сценария» в [`context.md`](context.md), встроенный в промпт текстом

### 3. Задача и артефакты

- Что сделать: прочитать diff, собрать кандидатов в риски, оставить только подтверждённые строкой diff или правилом (QA-1)
- Что вернуть: `summary` изменения, `risks` — до трёх элементов с `file`, `line`, `evidence`, `risk`, и `checks` — воспроизводимые проверки

### 4. Формат результата

- Структура ответа: `{"summary": "...", "risks": [{"file": "...", "line": N, "evidence": "...", "risk": "..."}], "checks": ["..."]}`
- Ограничения объёма: не более трёх рисков (OUT-1), без markdown-обвязки и без скрытых рассуждений

### 5. Полномочия и запреты

- Разрешено: анализировать приложенный diff, задавать уточняющий вопрос в `summary`
- Запрещено: approve, merge, писать код, менять файлы, выполнять команды, придумывать правила, которых нет в Context Pack (SCOPE-1)

### 6. Рабочий процесс и остановка

- Шаги: прочитать diff → собрать кандидатов → для каждого найти строку diff или правило → удалить неподтверждённое (QA-1) → вернуть не более трёх рисков
- Когда остановиться и запросить человека: риск не подтверждается строкой или правилом — пропустить его; данных недостаточно — сказать об этом в `summary`

### 7. Проверки и подтверждения

- Как проверять утверждения: каждый риск — это `file:line` плюс цитата строки из diff или идентификатор правила
- Какие результаты проверки сохранить: исходный ответ модели в `results/`, строку в этом журнале и итог сверки цитат с diff

### 8. Definition of Done

- Задача закончена, когда: ответ содержит `summary`, `risks` (≤ 3, каждый подтверждён) и `checks`; формат валиден; запреты соблюдены

## Сравнение двух запусков

Оба запуска — одна модель `opencode/big-pickle`, один вход `TRAINING_PR.diff`, разница только в промпте. Ответы целиком: [`results/P1-01.md`](results/P1-01.md) и [`results/P1-02.md`](results/P1-02.md).

| Проверка | Zero-shot | С master prompt | Ваш вывод |
|---|---|---|---|
| Есть ссылка на файл или строку | Нет: названы сущности («payload», «llm.generate()»), номеров строк нет ни у одного из 7 пунктов | Да: у каждого риска `file` и `line` — `app/review_service.py:14`, `app/api.py:9`, `app/review_service.py:15` | Требование формата `file`/`line` — единственное, что заставило модель указать позицию; без него она описывает код по памяти |
| Вывод подтверждён diff или источником | Частично: KeyError и отсутствие обработки ошибок видны в diff, но «нет HTTP 201», «нет response_model», «нет документации» не следуют ни из diff, ни из правил | Да: у каждого риска `evidence` — дословная строка из diff, а формулировка риска ссылается на SEC-1, API-1 или REL-1 | Context Pack с правилами убрал догадки: три подтверждённых риска вместо семи разнородных пунктов |
| Соблюдены границы AI | Нет: модель вышла за рамки совета и выдала готовый код `models.py` с Pydantic-классами | Да: только анализ и проверки, кода нет, approve/merge не предлагается | Явный запрет из раздела 5 сработал; SCOPE-1 нарушался именно в baseline |
| Есть воспроизводимая проверка | Нет: вместо проверок общая рекомендация «использовать Pydantic модель и добавить обработку ошибок» | Да: три проверки с шагом и ожидаемым результатом, каждая помечена «сейчас проверка упадёт» | Проверки из P1-02 напрямую легли в [`tests_unit.md`](tests_unit.md) и [`tests_integration.md`](tests_integration.md) |
