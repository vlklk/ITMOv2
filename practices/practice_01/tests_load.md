# Нагрузочные проверки

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Назначение документа

Регламент нагрузочного тестирования FastAPI-сервиса AI-помощника ревьюера PR (`POST /api/reviews`, синхронный вызов внешнего LLM). Документ отвечает на четыре вопроса:

1. **Что считать успехом?** — числовые пороги в разделе «SLO и допустимые пороги» и в колонке «Допустимый предел».
2. **Что и как гонять?** — матрица из 16 сценариев, разбитая на три уровня по частоте и стоимости запуска.
3. **Чем доказываем результат?** — колонка «Подтверждение»: артефакты k6, снимки Grafana, трейсы APM, перехваченные промпты мок-LLM.
4. **Когда тесты можно интерпретировать?** — раздел «Готовность к запуску».

Версия до Практики 2 содержала два сценария и текст-заглушку «нагрузочное тестирование станет актуальным позже». Шесть техник промптинга применялись именно к этому файлу, журнал экспериментов — [`../practice_02/prompts.md`](../practice_02/prompts.md).

## Регламент

1. **Порядок прогона.** Всегда начинать со smoke и baseline. Capacity → peak → spike → stress запускаются только после зелёного baseline; soak — после подтверждённой точки насыщения. Проверки бизнес-правил выполняются в любом порядке после baseline.
2. **Контур вызова.** `POST /api/reviews` → очистка секретов (SEC-1) → вызов внешнего LLM с timeout 10 секунд (REL-1) → ответ в формате OUT-1. Фоновых очередей, воркеров и отдельной БД в сценариях нет: в [`context.md`](context.md) зафиксирован синхронный вызов.
3. **Фиксация условий.** Каждый прогон записывает версию сервиса (`git rev-parse HEAD`), окружение, версию сценария k6 и время старта. Без этой строки прогон не считается подтверждением.
4. **Хранение артефактов.** Результаты — `k6/results/<scenario>_<YYYY-MM-DD>.json`, снимки — `grafana/<scenario>-<YYYY-MM-DD>.png`, трейсы выгружаются из APM по `request_id` (OBS-1), перехваченные промпты — `mocks/captured_prompts/<scenario>.jsonl`.
5. **Повторяемость.** Сценарии, зависящие от LLM, гоняются на мок-LLM с детерминированной задержкой. Прогон на реальном провайдере допускается отдельно — для валидации мока, но не вместо него.
6. **Регрессия.** Любое изменение кода требует повторного baseline. Ухудшение p95 более чем на 10% от предыдущего прогона того же сценария — Fail.
7. **Обновление.** Пороги пересматриваются при изменении правил в Context Pack [`context.md`](context.md) (SEC-1, API-1, REL-1, OUT-1, OBS-1).

## SLO и допустимые пороги

Применяются ко всем сценариям, если в матрице не указано иное.

| Метрика | Порог | Откуда порог |
|---|---|---|
| Латентность p95 | ≤ 8 секунд | REL-1 (timeout 10 с) с запасом 20% |
| Латентность p99 | ≤ 10 секунд | REL-1 — timeout внешнего LLM-вызова |
| Ошибки 5xx | 0% за прогон | REL-1 — ошибка LLM превращается в контролируемый ответ |
| Ошибки 4xx | только ожидаемые: 100% HTTP 413 при diff > 20 000 символов, HTTP 422 при невалидном payload | API-1, [`tests_e2e.md`](tests_e2e.md) |
| CPU | ≤ 70% в пике, без троттлинга | Запас на горизонтальное масштабирование до троттлинга |
| RAM | рост ≤ 20% от стартовой и стабилизация к концу прогона | Практика soak-тестирования: линейный рост = утечка |
| Утечки секретов | 0 вхождений тестового токена в перехваченных промптах | SEC-1 |
| Конформность ответа | 100% ответов с `summary`, `risks` (≤ 3), `checks` | OUT-1 |
| Контракт лога | 100% записей содержат `request_id`, `duration`, `status`; 0 вхождений тела diff или ответа | OBS-1 |

## Готовность к запуску

Нагрузочные сценарии разрешаются по мере готовности инкрементов из [`project_management.md`](project_management.md) — до этого их результат нечем интерпретировать:

| Что доступно | Когда | Почему раньше нельзя |
|---|---|---|
| L1-1, L1-2 на мок-LLM | Сейчас | Измеряют стенд и тестовую обвязку, а не сервис: ни timeout, ни формат ответа ещё не реализованы |
| L1-3, L1-4, L1-5 | После инкремента 1 (валидация, лимит 20 000, очистка секретов) | Нечего проверять: сейчас нет ни 422, ни 413, ни фильтра секретов |
| L2-1 … L2-6 | После инкремента 2 (timeout 10 с, формат OUT-1) | Без timeout латентность не ограничена сверху, без OUT-1 нечего валидировать |
| L2-7, L3-1 … L3-4 | После инкремента 3 (логирование `request_id`, `duration`, `status`) | Длительные прогоны без структурированного лога и метрик невозможно разобрать |

## Что отклонили

- Сценарии read-heavy, write-heavy и mixed с GET-листингом ревью: в [`context.md`](context.md) и `TRAINING_PR.diff` есть только `POST /api/reviews`, GET-эндпоинта нет.
- Сценарии с очередями сообщений, фоновыми воркерами и конкуренцией за БД: контур синхронный, база данных в кейс не входит.
- Формулировки без числового порога («система выдерживает нагрузку», «должно быть быстро») и сценарии без артефакта в колонке «Подтверждение».
